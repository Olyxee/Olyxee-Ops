Implement a production-ready **Resend email notification system** in Olyxee Ops.

Resend is already connected to our Olyxee domain. Build the application integration around it.

The goal is:

`Important event happens in Ops → correct person receives a concise email → email links them back into Ops`

Do not make email the source of truth. The actual task, review, user, and internship state must remain inside Olyxee Ops.

## 1. Environment Configuration

Use environment variables for all email configuration.

Required variables:

```env
RESEND_API_KEY=
EMAIL_FROM=
EMAIL_REPLY_TO=
OPS_APP_URL=
```

Example values:

```env
EMAIL_FROM="Olyxee Ops <ops@olyxee.com>"
EMAIL_REPLY_TO="ops@olyxee.com"
OPS_APP_URL="https://ops.olyxee.com"
```

Do not hard-code:

* API keys
* domain names
* production URLs
* sender addresses

Validate required environment variables on backend startup.

Never expose `RESEND_API_KEY` to the frontend.

## 2. Central Notification Service

Do not call Resend directly from React components or random API handlers.

Create a centralized backend notification/email service.

Suggested structure:

```text
server/
  services/
    notifications/
      emailService
      templates
      events
```

Exact paths can follow the existing project architecture.

The email service should handle:

* Resend API calls
* recipient validation
* sender configuration
* template rendering
* logging
* failures
* retries
* deduplication where necessary

Create a reusable function conceptually like:

```ts
sendTransactionalEmail({
  type,
  recipient,
  subject,
  templateData,
  relatedUserId,
  relatedTaskId
})
```

Adapt this to the existing stack.

## 3. Notification Events

Create centralized application events for:

Avoid tightly coupling task CRUD logic directly to Resend.

## 4. New Account Email

When a Superadmin or authorized Manager creates a new Ops user, automatically send an onboarding email.

Do NOT email a permanent password.

Preferred flow:

1. Create user account.
2. Generate secure account setup/password creation token.
3. Token should expire.
4. Send user a secure setup link.
5. User creates their password.
6. Mark setup token as used.

Email subject:

```text
Your Olyxee Ops account is ready
```

Email content must include:

* user's first name
* role
* department if available
* login email
* button: `Set up your account`
* Olyxee Ops URL
* expiry information for setup link

Example destination:

```text
https://ops.olyxee.com/setup-account?token=...
```

Use the application's existing auth/password-reset mechanism where possible instead of creating a second security system.

If the application already uses Supabase Auth, Firebase, Clerk, Auth.js or another auth provider, integrate with its secure invite/reset flow instead of inventing custom password handling.

## 5. Account Creation Must Not Fail Because Email Failed

If account creation succeeds but Resend fails:

* keep the user account
* record email as failed
* allow retry
* do not rollback the account

Show the Superadmin/Manager something like:

```text
Account created. Invitation email could not be delivered.
```

Provide:

`Resend invitation`

Do not expose technical provider errors directly to normal users.

## 13. Due-Date Notifications

Implement scheduled due-date email processing.

Send:

### Due tomorrow

Subject:

```text

```

### Overdue

Subject:

```text

```

Example deduplication identity:

```text

```

If the due date changes, future reminders should use the new date.

## 20. Retry Behaviour

Implement safe retry behaviour for failed transactional emails.

Use a reasonable retry limit.

Do not create infinite retry loops.

Retrying must not create duplicate audit records or trigger duplicate business actions.

For example, retrying an email must not resubmit a task.

## 21. Idempotency / Duplicate Protection

This is important.

Prevent duplicate emails caused by:

* React re-renders
* API retries
* page refreshes
* duplicate requests
* background job reruns

Use backend-generated notification events and deduplication keys.

For example:

```text
task-submitted:[taskId]:[submissionId]
```

or:

```text
account-invite:[userId]:[inviteVersion]
```

If the same event is processed again, do not send the same email twice.
